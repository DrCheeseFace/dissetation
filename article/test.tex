\section{Introduction}
\subsection{Motivation}
The workflow of a data-scientist typically follows the following order of
tasks. 
\begin{enumerate}
        \item Capturing of data
        \item Preprocessing of data 
        \item Exploratory analysis 
        \item Final analysis 
\end{enumerate}

The majority of time out of this workflow is consumed by the preprocessing of
data step. As shown in \cite[p~3 fig~2]{sarih_data_2019} the cleaning and
organizing of data takes up an estimated 60\% of a data-scientists time. This
is a manual process that requires human judgement. This critical step requires
tedious and rigorous testing; In particular, low-quality data imputation can
result in unnatural or even worse, misleading distributions of values. The side
effects of which can include poorly performing prediction models and inaccurate
exploratory and final analysis. Data imputation started with simple methods
such as mean/median imputation. With the discovery of the mechanics of missing
data and concepts such as MCAR (missing completely at random), MAR (missing at
random) and MNAR (missing not at random) \cite{little_statistical_2019}, data
scientists now have access to a large array of complex algorithms to choose
from, which each have their own positives and drawbacks. Picking the optimal
algorithm for imputation for each feature in a dataset is time-consuming and
prone to error. 

While applications in the past have been developed to ease data imputation,
such as VIM \cite{templ_exploring_2012}, MANET \cite{unwin_interactive_1996}
and AmeliaView \cite{honaker_amelia_2024}, there has been little development in
the way of comparing different imputations of the same dataset. Currently, the
solution for comparing different imputation results would be to manually create
separate scripts for each imputation method and then, using the created
versions of the datasets, compare them using graphs. 

Older applications, such as the ones
mentioned before lack newly discovered visualization methods such as MissiG
\cite{fernstad_explore_2022} that could prove to be more useful for analyzing
missingness of data. 

\subsection{Aims} 

This project aims to:
\begin{itemize} 

        \item Make the decision-making step for data imputation easier by
                providing a touch screen dashboard interface for comparing
                different imputation results that are derived from different
                algorithms of imputation. 

        \item Reduce the time spent on the preprocessing of datasets as well as
                improve the results of imputed datasets.

        \item Create a solution for keeping track of combinations of
                imputations performed on versions of datasets created from
                prior imputations in a GIT \cite{noauthor_git_nodate} style
                version control system. 

\end{itemize}

\subsection{Objectives}

\begin{enumerate}

\item \textbf{Missingness Structures} - This dissertation will investigate and
        explain the concept of missingness structures and its role in data
        imputation and analysis. It will explain the different types of missing
        data as well as provide examples via synthetically created missing
        data.

\item \textbf{Missing Data Visualizations} - This dissertation will talk about
        methods of missing data visualizations. It will also provide
        implementations of discussed visualizations. 
        
\item \textbf{Imputation Version Control} - This dissertation will propose a
        method of keeping track of imputed datasets, discussing an example
        use case as well as implementation details.

\item \textbf{Web App Implementation and User-flow} - The main created artifact
        of this dissertation is a web app to impute and compare imputed
        datasets. Features and an example user-flow will be presented.

\end{enumerate}

\section{Background Review}
This part covers the background research gone into the design of the main
artifact \emph{MICA} and the synthetic missing data generator.
\subsection{The Nature of Missing Data Structures}

For the below figure examples, the UCI Irvine Heart Disease dataset
\cite{andras_janosi_heart_1989} was used as a base with missingness mechanisms
and patterns synthetically added after. 

There are two parts to go over for understanding how to tackle missing data. 
\begin{enumerate}
        \item \textit{Missingness mechanisms}
        \item \textit{Missingness patterns}
\end{enumerate}

\subsubsection{Missingness mechanism}
As explained in \cite{rubin_inference_1976}, a missingness mechanism is defined
as why data is missing depending on other variables observed as well as the
missing variable itself. Analyzing why data is missing is crucial in finding
the best method of to deal with missing values as if we were to assume data is
always \textit{Missing Completely at Random}, we can skew distributions of
features unintentionally. We have three categories to describe the types of
missingness mechanisms.

\paragraph{\textbf{Missing Completely at Random (MCAR)}}~\\ 
MCAR is a missingness mechanism where missing values are not related to other
recorded or unrecorded data. This is the least severe of the three missingness
mechanisms as you are able to impute the dataset without causing large
unintended side effects without knowing the underlying mechanism of why the
data is missing. Dropping records with missing values will not affect the
distribution of the variables greatly. \eg
\cref{fig:distribution_lines_age_MCAR}. 

Being able to easily identify MCAR using visualizations and statistics via
developer tooling would be a feature to look for in the design and
implementation of \mica.


\begin{figure}[H]
    \centering
        \includegraphics[width=0.8\textwidth]{distribution_lines_age_MCAR.png}
        \caption{MCAR mechanism Age distribution before and after dropping missing values}
    \label{fig:distribution_lines_age_MCAR}
\end{figure}

\paragraph{\textbf{Missing at Random (MAR)}}~\\ 
MAR is a missingness mechanism where missing values are related to other
observed values. Handling MAR is more nuanced as compared to MCAR as we can
introduce biases if we naively drop records containing missing values
\cref{fig:distribution_lines_age_MAR}.

Similar to MCAR, we most likely still do not need to know the underlying cause
of the missing values in order to impute the data as we can use Multivariate
imputation algorithms such as KNN and MICE \cite{buuren_mice_2011} to estimate these.

\begin{figure}[H]
    \centering
        \includegraphics[width=0.8\textwidth]{distribution_lines_age_MAR.png}
        \caption{MAR mechanism Age distribution before and after dropping missing values}
    \label{fig:distribution_lines_age_MAR}
\end{figure}

\paragraph{\textbf{Missing Not at Random (MNAR)}}~\\ 
MNAR is a missingness mechanism where the likelihood of a value being missing
is dependent on unobserved values. Out of the three missingness mechanisms,
this is the most severe as knowledge of the underlying cause of the missing
data is required to perform data imputation. MNAR suggests there could be fault
in the data gathering process. WHO TO CITE FOR THIS?.

\subsubsection{Missingness patterns}
Missingness patterns are a derivation of \emph{missingness mechanism} that is
more easily identifiable and actionable by a data scientist working on a data
analytics task with missing variables. Fernstad \cite{fernstad_identify_2019}
defines three specific characteristics of missing data to look for.
\begin{enumerate}
        \item \textit{Amount Missing}
        \item \textit{Joint Missingness}
        \item \textit{Conditional Missingness}
\end{enumerate}

\paragraph{\textbf{Amount Missing}}~\\
The \textit{Amount missing} describes the percentage missing of a selected variable out of
all records in a dataset. This is useful to know in a practical sense as that
data engineers need to know what variables are worth imputing and discarding.
We can also use this to identify or dismiss the \textit{MCAR} missingness
mechanism for a variable. 

\begin{figure}[H]
    \centering
    \begin{subfigure}[H]{\textwidth}
        \centering
        \includegraphics[width=\textwidth]{MCAR_recorded_age_distribution.png}
        \caption{Recorded age values.}
    \end{subfigure}\hfill
    \begin{subfigure}[H]{\textwidth}
        \centering
        \includegraphics[width=\textwidth]{MCAR_missing_hd_age_distribution.png}
        \caption{Age when Heart Disease is missing.}
    \end{subfigure}
    \caption{Comparison of age distributions across the dataset; MCAR mechanism}
    \label{fig:MCAR_age_comparison}
\end{figure}

As seen in \cref{fig:MCAR_age_comparison}, the distribution of \textbf{Age} and
the distribution of \textbf{Age if Heart Disease is missing} show similar
distributions as mathematically described by a low Wasserstein distance of
\textbf{0.1174}. This indicates a high likelihood of the missingness mechanism
present being MCAR. 



\begin{figure}[H]
    \centering
    \begin{subfigure}[H]{\textwidth}
        \centering
        \includegraphics[width=\textwidth]{MAR_recorded_age_distribution.png}
        \caption{Recorded age values.}

    \end{subfigure}
    \begin{subfigure}[H]{\textwidth}

        \includegraphics[width=\textwidth]{MAR_missing_hd_age_distribution.png}

Contrarily in \cref{fig:MAR_age_comparison} we get a Wasserstein distance of
\textbf{6.9925}, describing a large difference in distribution between the two
Age frequency histograms. For a data scientist practitioner, this can rule out
MCAR and they can look into verifying the nature of the missingness mechanism
of the missing variable. 



\paragraph{\textbf{Joint Missingness}} ~\\ 
A \textit{Joint missingness} pattern refers to the likelihood of a variable
being missing if one or more other variables are also missing. Finding evidence
of joint missingness, suggests the presence of the MNAR mechanism. This can be
expressed with the use of a heatmap. 

\begin{figure}[H]
    \centering
        \includegraphics[width=0.9\textwidth]{JM.png}
        \caption{Joint Missingness depicted via Heatmap
        \cite{bilogur_residentmariomissingno_2026}}
    \label{fig:JM}
\end{figure}

For the given example \cref{fig:JM}, \textbf{30\%} of Age values are missing;
If Age is missing, \textbf{80\%} of Max Hr values are missing. MCAR was added
after at a rate of \textbf{20\%}. The blue intersecting block shows a nullity
correlation between Age and Max Hr of \textbf{0.5}.

\paragraph{\textbf{Conditional Missingness}} ~\\ 
A \textit{Conditional missingness} pattern refers to the likelihood of a
variable being missing depending on the value of another variable. This is more
tricky to visualize as instead of its likelihood of being missing being
dependent on the likelihood of other variables being missing as in
\textit{Joint Missingness}, we need a way to visualize the values of a variable
compared to the relative missingness of a variable. Finding evidence of
\textit{Conditional Missingness} suggests the presence of a MAR mechanism.

\begin{figure}[H]
    \centering
        \includegraphics[width=0.9\textwidth]{conditional_missingness_MAR.png}
        \caption{Conditional missingness of Age dependent on Max HR}
    \label{fig:conditional_missingness_MAR}
\end{figure}

The above \cref{fig:conditional_missingness_MAR} is a synthetically created
example of conditional missingness with the following rules \ref{conditionalmissingness}: 

Let $M_i$ be the missingness indicator for the $i$-th observation, where $M_i =
1$ if $\text{Max\_HR}$ is missing and $M_i = 0$ if it is observed. Let $A_i$
represent the age of the individual. The missing data mechanism is defined as:

\begin{equation}
\label{conditionalmissingness}
P(M_i = 1 \mid A_i) = 
\begin{cases} 
    0.7 & \text{if } A_i > 55 \\
    0   & \text{if } A_i \le 55 
\end{cases}
\end{equation}

\subsection{Visualizing Missing Data}
Fernstad's study \cite{fernstad_identify_2019} into the effectiveness of
certain visualization methods in relation to how well participants are able to
identify missingness patterns can help make suggestions into what visualization
methods would be beneficial to provide in the implementation of \mica.
The user-study test how well participants are able to identify missingness
patterns with the use of three visualization methods. 

\begin{enumerate}
        \item Marginplot Matrix
        \item Parallel Coordinates
        \item Matrix Plot 
\end{enumerate}

Both Matrix plot and Parallel Coordinates performed significantly better as
compared to Marginplot in identifying missingness patterns \cite[Table
4]{fernstad_identify_2019}. Fernstad argues for the importance of clear
frequency representation as well as the benefits of not separating recorded and
unrecorded values in regard to being able to identify \textit{Conditional
Missingness}.

of a Heatmap and Parallel Coordinates.

The uniquely interactive component of MissiG as well as its superior
performance for identifying missingness patterns makes this visualization
especially suited for use in \mica.

\subsection{Imputation Techniques}

\subsection{Previous Implementations}
Many examples of imputation applications exist. These include VIM, Amelia view
\cite{honaker_amelia_2024} and Profiler, but these applications focus on analyzing
singular imputations and do not take into account the broader picture of
comparing imputation results and managing versions. One novel example
Impute-VSS \cite{shrivastava_impute-vss_2025} by Shrivastava et al. exists and
worth analyzing as it uses comparative visualizations to deduce the
effectiveness of different methods of imputation at once.

\paragraph{\textbf{Impute-VSS}}~\\
Impute-VSS's novel feature is the \textit{comparative imputation assessment};
this allows the user to perform a series of multivariate and univariate
imputation methods and compare the results with each other. Impute-VSS offers
five visualization methods for the user to use when picking the optimal
imputation results.

\begin{itemize}
        \item Histogram
        \item Missing Bars
        \item KDE
        \item Box Plot
        \item Correlation line graph
\end{itemize}

Although these visualizations are good for understanding the change in
distributions of a single variable, the user is not able to effectively see the
change in correlations between variables. As mentioned previously, the three
missingness patterns a data engineer would look for are \textit{amount missing,
Joint Missingness} and \texitit{condition missingness}. There is a lack of
visualizations pertaining to displaying information about \texit{amount
missing}. \itemit{Joint missingness} is somewhat visualized to the user with
the use of a "Missing Bars" plot although due to the format, for numerous of
features in a dataset, this can be clunky and hard for the user to spot the
joint missingness pattern. \itexit{Conditional missingness} is not visualized
with any of the provided graphs in Impute-VSS. This is especially problematic
as conditional missingness patterns usually signify the presence of a MNAR
mechanism which as discussed previously cannot be ignored and has to be
explicitly handled by the data engineer in order to not introduce any unwanted
biases in the data.

Although Impute-VSS allows for the comparison of imputation techniques, the
user is unable to test out how different imputation steps affect each other as
the user is only able to compare a single step imputation process. This omits
the possibility of multiple occurrences of missingness patterns that require
separate methods of imputation. \eg Joint missingness between variables A and B
as well as another instance of joint missingness between variables C and D.

Impute-VSS also provides a comparison of calculated metrics between the dataset
versions. 

Overall although Impute-VSS has employed a variety of visualizations and
metrics for use in analyzing imputed datasets, it lacks newly developed
missing data visualization research and consequently visualizations.

\subsection{Technology Stack Evaluation}
There are two main data science libraries used commonly mentioned in the above
applications. The older applications such as Amelia View use the VIM R package.
This uses optimized C++ code to perform the bulk of the computationally heavy
operations. Due to its age and prevalent use, a lot of testing has gone into
improving the reliability of the implementations. New applications such as
Profile and Impute-VSS use the python library Scikit-learn as well as scipy for
computations such as KNN and metric formulas. These use Cython which is
comparable to the performance of C++ code.

Both Profile and Impute-VSS use a two stack architecture. Both frontend and
backend are split into layers that handle the UI and logic respectively.
Profiler has opted for a more performance biased design when it comes to the
engineering decisions regarding the frontend. D3.js is used to render SVG's
with the use of drag-and-drop and menu-based interface to offer an interactive
experience to the user. 

\subsection{Requirements}
Using the above background research, \mica's requirements can be defined as
such.

\subsubsection{Functional Requirements}

\begin{enumerate}[label=F.R.\arabic*]
        \item \textbf{Data Ingestion and Export:} \mica must allow users to
                upload datasets to process the data and also allow for the
                download of imputed versions of that dataset.

        \item \textbf{Imputation Methods:} \mica must provide both multivariate
                imputations such as KNN and MICE as well as univariate
                imputation methods such as Mean, Median, Mode.

        \item \textbf{Parameter Configuration:} \mica must allow users to
                manually configure parameters relevant to the imputation method
                performed. \eg Tuning N nearest neighbors value for the KNN
                imputation method.

        \item \textbf{Pre-Imputation Visualization:} \mica must provide an
                interactive MissiG implementation with the ability to generate
                charts for each dataset version accessible to the user.

        \item \textbf{Version Control Operations:} \mica must track imputations
                applied to a dataset using a strict hierarchical tree
                structure. Users are given the functions to perform the basic
                version control actions of applying, deleting and reverting
                changes to a specific historical node.

        \item \textbf{Comparative Visualizations:} \mica must allow the user to
                select at least 2 unique versions of the dataset and generate
                comparative visualizations, specifically an interactive
                Parallel Coordinates graph and a Missingness Matrix.

        \item \textbf{Statistical Metric Computation:} \mica must provide the
                user with comparative distribution metrics between two selected
                dataset versions.
\end{enumerate}

\subsubsection{Non-Functional Requirements}

\begin{enumerate}[label=N.F.R.\arabic*]

        \item \textbf{Performance and Latency:} \mica's frontend client must be
                performant and responsive by caching computationally difficult
                visualization data and minimizing DOM changes.

        \item \textbf{Usability / Accessibility:} All navigation and actions
                must be accessible by a touchscreen and only require a
                touchscreen.  

        \item \textbf{Modularity and Extensibility:} \mica's API and Impute
                Handler must be designed with a decoupled architecture so
                future development such as supporting further imputation
                methods, can be integrated without requiring breaking changes
                to the API.

        \item \textbf{Portability:} \mica's software components must be
                containerized using Docker. This allows for consistent
                deployment across different environments.

        \item \textbf{Computational Efficiency:} Imputation methods and heavy
                metric calculations must be completed using computationally
                efficient algorithms and implementations.

        \item \textbf{Storage Optimization:} Unused and inaccessible dataset
                versions must be cleaned up by the \mica API in order to save
                secondary storage space.
\end{enumerate}

\subsubsection{MICA API}
\mica provides a simple-to-use API for uploading, imputing and managing
versions of imputed datasets. This is routed through an NGINX reverse proxy to
provide in the future RESTful API version sub-routing. The MICA API handles the
imputation versioning system. This acts as the bridge between the frontend
client and the impute handler. \mica API design has allowed for the
addition of other currently unimplemented imputation methods without needing 
breaking changes.

\subsubsection{Impute Handler}
Imputation logic as well as data required to draw graphs in the frontend client
are calculated within the impute handler. Scikit-learn
\cite{pedregosa_scikit-learn_2011} handles KNN and MICE imputation. The
Scikit-learn imputation library was picked for use in \mica as the core
functions are written in PYX syntax and proven to be highly optimized.
Likewise, scipy TODO REFERENCE HERE for various metrics implementations. Custom
functions as well as custom JSON representations are used to send information
back to the MICA API; This includes a novel JSON standard for the MissiG
visualization. 

\subsubsection{Frontend Client}
This utilizes D3.js \cite{noauthor_d3d3_2026} for drawing and rendering SVG
chart components. D3.js was chosen as it provides low-level tooling to enable
the development of novel visualizations such as MissiG. To maintain a stateful
manner in the frontend, \mica uses React  \cite{noauthor_react_nodate}
+ MobX  \cite{noauthor_about_nodate} to cache results requested from the MICA
API. For low latency interactability, \mica uses Shadcn-ui
\cite{noauthor_shadcn-uiui_2026} for styling as it is performant.

\subsection{Imputation Versioning System}
MICA introduces a novel way to track dataset versions in regard to imputations
performed on said dataset.
\subsubsection*{The Problem}
The typical workflow of a data imputation task is an iterative process where
developers will need to create different versions of a dataset with varying
methods of imputation. With these different versions, in order to select the
best method of imputation, the user will need to create custom scripts
every time they would like to compare outputs. This process is tedious and
time-consuming. The process gets particularly complex when you have to keep
track of more than one imputation's difference between versions. 

For example, the below node diagram \cref{fig:nodegraph} depicts the history of imputations
performed on the dataset (root node). The cognitive overhead of keeping track
of the difference between nodes D and C's history can be prone to error due to
its complexity.

\begin{figure}[H]
    \centering
        \includegraphics[width=0.5\textwidth]{nodegraph.png}
        \caption{Example version history node graph representation}
    \label{fig:nodegraph}
\end{figure}

\subsubsection*{The Solution}

When a request to impute a dataset is sent from the client to the MICA API, the
operations are done in the following order.
\begin{enumerate}
\item Request is sent to MICA API.
\item Request is validated and passed onto the impute handler.
\item Impute handler creates version of dataset and returns err code.
\item MICA API creates hash for new dataset version and stores information on imputation.
\item MICA API returns err code and new version history information to client.
\end{enumerate}

To store the history of a data imputation, \mica uses a hierarchical
strict tree structure. Since in some cases, imputation order matters, a tree
data structure is suited for this problem as it inherently stores child\\parent
information and no sideways or backwards connections are allowed.


\subsection{UI Implementation}
\mica's UI is split into three tabs that aims to push the user into a simple
linear workflow.
\begin{enumerate}
        \item Pre-imputation Analytics (MissiG view)
        \item Imputation tab
        \item Post-imputation Analytics (comparative visualizations) 
\end{enumerate}

All actions in \mica are accessible by a touchscreen interface. File names are
automatically generated based on imputations requested by the user as well as
manually editable if the user would wish to give a custom name for a particular
version of a dataset.

MICA API includes a custom data structure for describing a MissiG
visualization. Numeric and Categorical data is handled with different histogram
data structure implementations.

To improve readability from the users' perspective, the amount missing and joint
missingness percentage was calculated for each card. This is then displayed at
the bottom of each glyph for the user to reference when analyzing a dataset.

Due to \mica's requirement of being low latency, the design decision to cache
these results in the frontend client was taken for the cost of greater memory
usage. This is necessary as the MissiG visualization generates a joint
missingness histogram for every pair of variables. Consequently, the total
number of generated histograms scales quadratically, at \( O(n^2) \) , relative
to the number of variables. If we were to request the MICA API to load this
data for every access instance, the latency will become noticeable and cause
unneeded load on the MICA API and Impute Handler containers.

\subsubsection{Imputation}
\mica currently provides five imputations methods. Due to the modular design,
the addition of further imputation methods is trivial. 

For columnwise imputation, Mean, Median and Mode is provided. These were
implemented manually with the use of the python package Pandas
\cite{noauthor_pandas_nodate}.

\mica provides 2 multivariate imputation options; KNN and MICE. KNN has the
added parameter N nearest-neighbors for the user to adjust manually. MICE in
the future could be expanded to allow the user to select the estimator; In the
current implementation, this is defaulted to use the following 
\begin{verbatim}
    RandomForestRegressor(

        min_samples_leaf=1,
        min_weight_fraction_leaf=0.0,
        max_features=1.0,
        max_leaf_nodes=None,
        min_impurity_decrease=0.0,

\end{verbatim}

\subsubsection{Post-Imputation Analytics}
The imputation version history is represented in a timeline format going from
oldest at the top and newest at the bottom \cref{fig:commithistory}. For each

For each node on the commit history, a revert button is assigned to it; This
calls the MICA API endpoint that reverts history to a specific file hash. Doing
so will delete all children of this file hash in order to save storage. Each node
also has a dropdown to display cards showing applied imputations to that
particular version of the dataset, from oldest to newest imputation. A
comparison selector toggle is also provided, so the user can pick a dataset to
include in a comparison visualization.

\paragraph{\textbf{Parallel Coordinates}} ~\\ 
The first visualization presented to the user is an interactive parallel
coordinates graph comparison widget \cref{fig:parallelCoordinatesCompare}. This
was implemented from scratch using the D3.js visualization toolkit. A random
sample of indexes is taken out of both datasets and displayed; matching indexes
are used as the difference in each graph should only be in features which have
been affected by the difference in imputations between the two datasets. Each
parallel coordinate visualization of the dataset is overlaid in contrasting
blue and red. Three buttons are provided for the user to switch between
displaying both graphs or either of the graphs by itself. The interface assists
in the detection of meaningful correlations, providing the clarity necessary to
differentiate signal from data noise

In addition to a standard Parallel Coordinates visualization, to indicate the
presence of a missing value, if a value is missing for a feature, a purple line
is drawn to the top of the axis.

The main drawback of using this visualization is that order matters; it can be
difficult for the user to spot correlations when the two features with
correlations are on opposite ends of the graph. This has been mitigated by the
implementation of the drag and drop reordering feature. With this feature,
users are able to try out different orders of features in order to find
correlations between features they would not have found otherwise.

\paragraph{\textbf{Missingness Matrix}} ~\\ 
The second visualization presented to the user is a missingness matrix dialog
\cref{fig:missingnessmatrix}. This was implemented as a custom D3.js component.
Similar to the parallel coordinates' implementation, a down sampled version of
the dataset is taken to reduce render time and avoid excessive memory usage. As
described by Fernstand \cite{fernstad_identify_2019}, each drawn column
represents a feature within a given dataset and cells within columns are colors
light gray for low values and dark gray for high values. Missing values are
represented as red cells. As posited by Fernstad this may make it easy for a
user to spot patterns between recorded and missing data. The use of an on hover
tooltip allows the user to access information such as feature name and index
number the cell representing.

An added functionality was added on top of this base to utilize the interactive
aspect of \mica. The user will be able to sort columns by a particular cells'
magnitude. This is useful for cases where we want to analyze a conditional
missingness pattern. \eg. $P(\text{feature}_y = \text{NaN} \mid
\text{feature}_x > c) = \theta$. For such a case, when the user sorts
$feature_x$, red bars (missing values) will be grouped together in the
$feature_y$ column, clearly signifying to the user that a conditional
missingness pattern is present. To pair with this additional feature was also
added to bubble records with missing values for a selected column to the top.
This is good for spotting joint missingness patterns as the user will be able
to see red blocks aligned between columns if the pattern is present. Both the
value magnitude and presence sorter is implemented using a toggle button on the
axis of each column.

A distribution metrics section
\cref{fig:comparison_imputations_and_distribution_metrics} was added to round
out the visualization methods provided. They are mathematically defined as follows: 

\textbf{Wasserstein Distance}

{\displaystyle W_{p}(\mu ,\nu )=\inf _{\gamma \in \Gamma (\mu ,\nu
)}\left(\mathbf {E} _{(x,y)\sim \gamma }d(x,y)^{p}\right)^{\frac {1}{p}},}

this metric describes how similar two distributions are to each other. In the
example a user performs an imputation and sees a high wasserstein distance, the
user knows the distribution of that select variable has changed dramatically
and may warrant further investigation.

\textbf{Kolmogorov-Smirnov Test} 

{\displaystyle F_{n}(x)={\frac {{\text{number of (elements in the sample}}\leq
x)}{n}}={\frac {1}{n}}\sum _{i=1}^{n}1_{(-\infty ,x]}(X_{i}),}

similar to the Wassserstein Distance, it
compares probability distributions. This is widely used in the data science
space to due its advantage of not assuming the shape of the distribution. A
limitation of the Kolmogorov-Smirnov Test is that it is more sensitive to changes
in the center and struggles to pick up on differences near the tails.

\textbf{Variance Ratio} 

\displaystyle {VAR\_RATIO} =
\frac{\sigma^2_{\text{child}}}{\sigma^2_{\text{base}}}

In the context of comparing different imputations of a dataset shows whether
one imputation method is smoothing the data more than the other. This is useful
when evaluating the risk of information loss and the preservation of natural
noise within the data. If we see a variance ratio significantly below one, this
may indicate that one of the imputation methods has artificially collapsed the
distribution. This can be used to verify if the other metrics provided are
worth looking at due to lower standard error.

\textbf{Skew Difference} 

\displaystyle \Delta \text{Skew} = \text{Skew}_{\text{base}} -
\text{Skew}_{\text{child}}

Skew Difference is the simplest to interpret out of the four. This shows the
direction and magnitude of the skew for a specified feature. 

In the comparison dialog two imputations cards are also displayed. This shows
the imputations performed on each version of the dataset. This also shows the
variable name and type of imputation. These cards are rendered in the order of
the performed imputations similar to the other implementations of this in
\mica.

\subsection{Synthetic Data Generation}

To assist in the development, testing and construction of the example
user-flow, synthetic data generation scripts were used to insert artificially
created missingness mechanisms and patterns into a dataset. This generated both
a full sized and down sampled versions of the UCI Irvine Heart Disease dataset
\cite{andras_janosi_heart_1989}. The larger datasets were used to test the
performance of \mica under strain. The smaller down sampled datasets were used
during the development and testing phase as a way to speed up the code/test
cycle. 


The missingness mechanisms and patterns have been defined and constructed as
such.

\subsubsection*{MCAR}
Two versions were generated for the MCAR mechanism; A regular and "varied"
version. The regular version contains both numerical and categorical data while
the varied version contains only numerical data. This was used as a way to
verify the rendering of categorical features as well as the backend handling of
categorical components was valid. This was required to verify the correctness
of the MissiG, Parallel Coordinate and Missingness matrix components as all
three visualizations required specific rendering requirements for categorical
data.

For MCAR, the conditions were such

\begin{equation} 
D_{i,j}^* = 
\begin{cases} 
\text{NaN} & \text{if } u_{i,j} < w_j \\ 
D_{i,j} & \text{otherwise} 
\end{cases}
\end{equation} 

\begin{itemize}
    \item $D_{i,j}^*$ represents the resulting value in the incomplete dataset.
    \item $D_{i,j}$ represents the original, observed value.
    \item $w_j$ is the predefined probability threshold for column $j$.
    \item $u_{i,j}$ is the random draw from a standard uniform distribution.
    \item \text{NaN} denotes the missing or undefined state.
\end{itemize}


\begin{description}
        \item [MissiG] We expect in the unselected feature the distribution of
                the missing values to roughly conform to the distribution of
                the recorded values when a glyph with missing values is
                selected. 

        \item [Parallel Coordinates] We expect the fully imputed and the MCAR
                variant to have a similar shape and show no major changes in
                the distribution. We also expect missing value lines to be
                spread evenly between all axes.

        \item [Missingness Matrix] We expect evenly distributions red bars that
                signify unrecorded values in columns where MCAR was applied to.
                Sorting by value magnitude and presence should show no
                patterns.
\end{description}


\subsubsection*{MAR}

For MAR, the conditions were such

\begin{equation} 
D_{i,j}^* = 
\begin{cases} 
\text{NaN} & \text{if } \text{Age}_i > 55 \land u_i < w_j \\ 
D_{i,j} & \text{otherwise} 
\end{cases}
\end{equation} 

\begin{itemize}
    \item $D_{i,j}^*$ represents the resulting value in the incomplete dataset.
    \item $D_{i,j}$ represents the original, observed value.
    \item $\text{Age}_i$ is the observed age for the $i$-th observation.
    \item $u_i$ is the shared random draw for row $i$ from a standard uniform distribution.
    \item $w_j$ is the predefined probability threshold for column $j$.
    \item \text{NaN} denotes the missing or undefined state.
\end{itemize}

\begin{description}
        \item [MissiG] We expect a hard drop-off in joint missingness histogram
                distribution for Age above 55 when another variable is
                selected. 

        \item [Parallel Coordinates] When the Age column is drag-and-dropped
                next to columns with missing values, we will see missing lines
                only diverging from the Age axis above the value 55. For all
                other columns, we will see missing lines coming out of the Age
                axis spread evenly.

        \item [Missingness Matrix] We expect missing values highlighted in red
                to appear exclusively in rows where $\text{Age} > 55$. If the
                matrix is sorted by the Age variable, this will be displayed as
                a completely solid block of observed data for ages 55 and
                under, followed by a visible scattering of missingness across
                other columns for the older demographic, distributed according
                to the column probabilities $w_j$.
\end{description}

\subsubsection*{MNAR}

For MNAR, the conditions were such:

\begin{equation} 
$$
D_{i,j}^* = 
\begin{cases} 
\text{NaN} & \text{if } (j = \text{Cholesterol} \land D_{i,j} > 250 \land u_{i,j} < 0.8) \\
           & \lor \: (j = \text{BP} \land D_{i,j} > 140 \land u_{i,j} < 0.8) \\
           & \lor \: (j = \text{Heart Disease} \land D_{i,j} = 1 \land u_{i,j} < 0.5) \\
D_{i,j} & \text{otherwise} 
\end{cases}
$$
\end{equation} 

\begin{itemize}
    \item $D_{i,j}^*$ represents the resulting value in the incomplete dataset.
    \item $D_{i,j}$ represents the original, observed value.
    \item $j$ identifies the specific variable column being evaluated.
    \item $u_{i,j}$ is an independent random draw for row $i$ and column $j$
            from a standard uniform distribution.
    \item \text{NaN} denotes the missing or undefined state.
\end{itemize}

\begin{description}
        \item [MissiG] We do not expect to see a visual difference between the
                red Histogram and the blue Histogram. Because the missingness
                is dependent on the variable's own values rather than the
                values of other variables, selecting a variable will not reveal
                a shift or pattern in the distribution of the remaining data.

        \item [Parallel Coordinates] We will see a concentration of purple
                lines (missing values) above the Cholesterol, BP and Heart
                Disease axis which then path out evenly to other features
                showing no correlation between the two features.

        \item [Missingness Matrix] Compared to the full dataset, we expect to
                see red blocks (missing values) clustered in areas that would
                otherwise be white (high values). If the matrix is sorted by
                Cholesterol or BP, there will be a clear transition from black
                (low values) to white, with a high density of red at the top of
                the gradient.
\end{description}

\subsubsection*{Joint Missingness}
To elaborate further into the type of patterns in the three visualizations that
exist when joint missingness is present, an MCAR mechanism was added
afterward.

For Joint Missingness, the conditions were such:

\begin{equation}
    \text{Age}_i^* = 
    \begin{cases} 
    \text{NaN} & \text{if } u_{i, \text{Age}} < 0.3 \\ 
    \text{Age}_i & \text{otherwise} 
    \end{cases}
\end{equation}

\begin{equation}
    \text{Max HR}_i^* = 
    \begin{cases} 
    \text{NaN} & \text{if } \text{Age}_i^* = \text{NaN} \land u_{i, \text{HR}} < 0.8 \\ 
    \text{Max HR}_i & \text{otherwise} 
    \end{cases}
\end{equation}

\begin{equation}
    X_{i,j}^{**} = 
    \begin{cases} 
    \text{NaN} & \text{if } \omega_{i,j} < 0.2 \\ 
    X_{i,j}^* & \text{otherwise} 
    \end{cases}
\end{equation}

\begin{itemize}
    \item $\text{Age}_i^*$ and $\text{Max HR}_i^*$ represent the values after
            the Joint Missingness process for the $i$-th observation.
    \item $\text{Age}_i$ and $\text{Max HR}_i$ represent the original, fully
            observed values.
    \item $u_{i, \text{Age}}$ and $u_{i, \text{HR}}$ are independent random
            draws from a standard uniform distribution $U(0,1)$ used for the JM
            conditions.
    \item $X_{i,j}^{**}$ represents the final state of the dataset after
            applying Missing Completely at Random (MCAR) noise to the JM
            results ($X_{i,j}^*$).
    \item $\omega_{i,j}$ is a random draw from a uniform distribution $U(0,1)$
            sampled for each cell $(i,j)$ in the data frame. 
    \item \text{NaN} denotes the missing or undefined state.
\end{itemize}


\begin{description}
        \item [MissiG] When switching the selected feature between Age and Max
                HR, we expect to see a high joint missingness percentage
                between the Age and Max HR features. Due to the added MCAR
                mechanism added throughout, we also expect to see a flat spot
                in the red histogram of Age. 

        \item [Parallel Coordinates] 
                We expect to see a large amount of purple lines in between Age
                and Max HR. The added MCAR will manifest as isolated purple
                lines across all features.

        \item [Missingness Matrix] 
                When Age is sorted by value presence, we expect to see matching
                missing blocks in Max Hr. We also expect to see randomly
                scattered red cells throughout due to the MCAR step in the
                synthetic missing data generation.
\end{description}

\section{Conclusion}
This part discuses the aims and objectives previously stated and confirms
whether they have been achieved or not as well as future work regarding \mica
and its related research.
\subsection{Aims and Objectives}
\subsubsection{Aims}
With regard to the main artifact, \mica provides a solution in three aspects.
\begin{itemize}
        \item \mica provides a touch screen interface for users to collaborate
                with other data scientists. This interface provides a variety
                of imputation algorithms as well as visualizations picked for
                the express purpose of data imputation.

        \item \mica utilizes state of the art, missing data research as well as
                newly developed visualizations in order to reduce the time
                spent on the preprocessing of datasets as well as make it
                easier for data science practitioners make the correct
                decisions when imputing a dataset.

        \item \mica introduces a novel way of handling versions of datasets by
                tracking imputations performed in a GIT version control style
                system. This aims to reduce confusion when handling multiple
                versions of imputed datasets and decrease the chances of making
                mistakes in regard to picking the most optimal imputation
                steps for a dataset.

\end{itemize}
\subsubsection{Objectives}

\begin{description}

        \item[\textbf{Missingness Structures}] This objective was met by
                researching and presenting the missingness mechanisms MCAR, MAR
                and MNAR as well as the missingness patterns amount, joint and
                conditional. The generation of synthetic missing data using the
                UCI Heart Disease dataset was used to visualize how missingness
                mechanisms and patterns appear in practical examples.

        \item[\textbf{Missing Data Visualizations}] This objective was met
                through the review of recently published researched on missing
                data visualizations as well as the implementation of three
                comparative visualization methods within \mica: A interactive
                implementation of a MissiG component, a custom Parallel
                Coordinate graph component and an interactive Missingness
                Matrix. These grouped together allow the user to visually spot
                missingness mechanisms and patterns and conclude what
                imputation method is most efficient.
        
        
        \item[\textbf{Imputation Version Control}] This objective was fulfilled
                by the engineering of a novel GIT styled version control system
                for tracking imputation methods performed on a dataset. The
                MICA API successfully manages the backend logic allowing data
                science practitioners to track, apply and branch different
                imputation operations and files without the cognitive overhead
                of recording files manually and keeping track of scripts.


        \item[\textbf{Web App Implementation and User-flow}] This objective was
                met by the creation of \mica, a fully implemented,
                containerized web application. By using a performant and
                decoupled technology stack, the application exhibits a
                low-latency intuitive interface that pushes users to a linear
                pre-imputation, imputation, and post-imputation step analytics
                workflow.

\end{description}

\subsection{Future Work} 

\mica currently supports only 5 methods of imputations. Adding further
imputation methods such as "hot-deck imputation" would be trivial with the use
of the sci-kit learn library and would greatly improve the functionality and
usability for data scientist practitioners. 

Further improvements on performance, particularly on optimizing JSON string
representations of custom data structures such as the one used for representing
a MissiG visualization, can help reduce latency on the client side as well as
reduce round-trip-time on requests made to the MICA API. 

Currently, multitouch gestures are unused within \mica; research and
implementations could be worth experimentation in order to further improve
usability. For example the ability to render large graphics and give the user
the ability to zoom in for greater clarity may prove useful for certain
visualization methods.

\mica currently only supports side by side comparisons of 2 different datasets
maximum. This limitation makes it hard for users to compare more than 2
different versions of imputation as the user is forced to switch between
comparing pairs of datasets instead of all at once in parallel. For complex
workflows this results in a cumbersome user experience. This can be addressed
by altering the currently implemented visualization components such as Parallel
Coordinates, to allow for an arbitrary number of dataset versions.

The current way \mica stores dataset versions is by creating a copy of every
dataset version in file storage. This is significantly inefficient especially
when handling large datasets. A proposed solution to this problem would be to
store only the \textit{diffs} of the changes applied to a dataset. This was not
implemented into \mica due to time constraints.

\mica utilizes React components to render its web app. This was picked for the
development of \mica as it allows for quick and simple implementations of
features. However, render times for React are slower compared to newly
developed web frameworks such as svelte. Memory usage also suffers as on idle
\mica uses a significant amount of primary storage as compared to plain HTML
and JavaScript or svelte. Rewriting the visualization components using a better
optimized web framework would make the user experience more responsive.
